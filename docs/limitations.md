# Known limitations

- Seasonal events, challenges, battlepass quests and milestone timers are not active; no seasonal rewards are granted. Delayed reward group reads return an empty mapping. Seasonal data reload and industry ticket redemption are independently refused, without changing data or consuming items. Seasonal login rewards are a separate implementation.
- Paid offers, raffle generation, ticket injection and cloud computing are not implemented. NES introduction reports the native inactive UNSET state, not completion. Reachable raffle QA and inventory ticket-injection requests are refused without consuming items; other external or gated calls have no handler. The existing monetization user-request acknowledgement does not load data or send a notification. Client-local feature-gate overrides are unsupported.
- Competitive tournament gameplay is deferred: the referee catalogue has no tournaments or systems, and match, detail and ship-list queries have no handler. The server sends no tournament ban notifications.
- The new player tutorial (AIR NPE) cannot run. Its dungeon layouts and behaviour trees never shipped with the client, so new characters start in their school's station.
- Operations tutorial progress and gameplay are not modelled: empty progress and no active category disable normal initialization; unsupported queries and actions are refused rather than pretending to succeed.
- Tutorial scene lookups return no destination or site, and position queries are refused; no tutorial instances are created. The QA level editor is unavailable and returns no editor object.
- Server node graph execution and QA controls are unavailable; subscriptions are empty and controls are refused.
- The QA mission-selection tool offers no missions.
- World-task gameplay and custom Agency content are unavailable. The task capability is closed and reads return zero data; if a client forces the panel open, the zero recovery timestamp may cause polling once per second.
- Daily-goal backend gameplay is implemented, but this change does not enable the final production client UI release flags or regeneration, expiry and slash controls; those release gates remain reserved for `daily-goals-release`. No real-client walkthrough or runtime proof is claimed. Faction-warfare goal schemas have no producer and are refused at activation into playable pools.
- Daily progress can remain pending until durable delivery catches up. When Lua or the required runtime is unavailable, daily operations fail closed rather than returning empty success; there is no mock fallback or automatic administrative reset. Rollover processes online pilots in bounded batches, not missed offline periods.
- Ship adaptation supports published tree and inactive mission reads, injector conversion and quoted LP exchange only. In the matching build, small, medium and large chip currencies have no physical injectors and this feature provides no positive acquisition path for them; existing balances remain readable and exchangeable when quoted. Unlocking nodes, assigning or QA-finishing tasks, and effects are refused without changes; no ISK, skills, SP or bonuses are granted. Retained historical chip reads work when adaptation content is disabled or unavailable, using the retained decoder without a live Lua Host; unrelated server startup prerequisites still apply. Unknown retained types are invariant errors, not silently omitted. Client source exposes an ordinary injector menu, but a normal exchange-window entry is unproved and client write-cache refresh is limited. Do not substitute a client patch, spoofed input material or QA calls for a normal UI walkthrough.
- [Remote service coverage](remote-services.md) lists the client calls that get a fixed answer instead of the feature, or are out of scope. QA starter-system overrides are not provided, so QA character creation uses the normal starter-system allocation, and the legacy petition window offers no character choices before a character is selected.

  - structure-docked `LeaveShip`, POS forcefield `SetShipPassword`, and POS/object-behalf targeting through `AddTargetOBO` or `RemoveTargetOBO`: these calls are refused without changes
  - rookie replacement and spare-kit grants at structures or in space; their actual-client button and hangar-refresh behavior is NOT VERIFIED
  - the real client clean-button interaction has not been verified; the documented dirt service protocol does not establish UI behavior
  - player structures: directory and profile views are empty; deployment, asset safety actions, control, docking and structure travel are refused
  - planetary colonies, extraction, launches and production: planetary reads expose only empty compatibility state and real planet metadata; resource data is not fabricated and gameplay remains unavailable
  - wars declared by one side, which need a war headquarters structure; war allies and surrender
  - full sovereignty gameplay: enemy capture of an owned Hub, vulnerability windows, development indices and activity defense multipliers, campaigns, command nodes and infrastructure upgrades are not implemented. Index reads do not fabricate numeric fallback values. Ordinary capital selection, pending changes and prime time are not implemented; only initial capital and current-capital loss are supported.
  - journal rows for ISK movements other than market cash movements and charged direct skill purchases; votes on a new CEO, war, share issue, expulsion or item locks, and acting on a vote's result; dividends paid equally to members
  - reactions and industry at player structures; NPC stations offer no reaction facility in the client
  - moon mining observers and the corporation tab of the mining ledger, which stays empty; the personal mining ledger works
  - moon extraction, automatic moon drilling, and structure compression or gas decompression; requests are refused where appropriate and consume no fuel, resources or items
  - starbases and control towers: the tower list is empty, and tower settings, permissions, moon and fuel factor requests are refused
  - fleet boosts, loading a saved fleet setup, removing unqualified members when arranging a wing by ship type, regrouping members who are not in their commander's system, and cynosural beacon broadcasts
  - beacon counts and faction-warfare kills on the star map
  - faction warfare enlistment, occupation, victory points and rewards, and shipcaster construction and travel; direct enlistment and leaving are refused, while dashboard reads return closed-state information
  - void-space and random filament travel are refused; interference is a closed display only, not an authorization for travel
  - surveys and PVP filament events are closed; no survey rewards or event queues are persisted, queue actions are refused, and event detail calls are deferred because no event data exists
  - amplification matrix skills, synchronization and cash deposits are unavailable; the HUD receives empty slots
  - brawl matchmaking, instances and gameplay are unavailable; actions are refused, and recovery reports OUTSIDE without creating character data or resetting the gateway controller
  - the Encounter Surveillance System: banks, links, reserve keys, payouts and their history; the Agency and system views show a closed ESS, and linking or unlocking a bank is refused with a message
  - fighter control: loading and unloading tubes, launching, recalling, moving, abandoning and using abilities are refused with a message, and no fighters appear in space
  - warp vectors: activation is refused
  - positional superweapon activations: single-point and slash activations are refused
  - in chat: password-protected channels, granting channel access to a whole corporation or alliance, taking over ownership of a system channel, and the local chat blackout in null-security space
  - access groups owned by a corporation, and access lists for structures
  - Alpha clone limits on skills, training speed, ships and modules, and planetary colony extraction rules: an Alpha account plays as an Omega one, except for seasonal login rewards, daily-goal eligibility and the daily Alpha skill injector
  - buying Omega time: only a GM can grant it, with `/clonegrade`
  - jump clones in ships and in player structures, and the body lost when a capsule is destroyed or a pilot self-destructs. The client does not include the server's clone-bay check: the server allows installation at NPC stations with a cloning service or a jump clone facility, and always applies the facility's standing restrictions, comparing raw standings rounded to two decimals as the client does. The Zarzakh facility refuses everyone, because faction-warfare enrolment is not modelled. Resetting the jump timer needs the GM or QA role.
  - external guard, SDK, RMT, authentication and payments: the guard address refusal can terminate the client guard worker after its local pipe opens; token-v1, browser authentication and redemption refusals can propagate where the client does not catch them. Browser authentication may have opened an external URL before its refused RPC.
  - face verification and webview authentication: the face-success callback has no catch, so its refusal may propagate as a callback or client exception; it does not invoke the failure callback, update its retry count, or terminate the app through that branch. The webview wrapper logs and rethrows the refusal and produces no proof.
  - EnvSDK moderation, QA platform tools, HTTP proxy and upload, anti-addiction history and cache tooling are not implemented. The client calls EnvSDK methods only when `envsdk_enabled` is on; the server never enables it, and turning it on locally is unsupported.
  - phone-number binding and its rewards, an external NetEase account service: the binding-success callback is answered but no binding is recorded
  - single-track login campaigns: none is open, and a claim reports that no reward was claimed; seasonal login rewards are unaffected
  - multi-character training activation: every character has an independent skill queue, so activation is unavailable and consumes nothing
  - character rename and re-sculpt cards are unavailable and refused without consuming anything
  - external reverse redemption, spam and bot reports, satisfaction votes and account QA actions are out of scope and refused; the client may update local spam-report state before the refusal
  - account token, user name, creation date, character energy and community track attribute calls remain unhandled rather than returning fabricated data. Client information gathering is disabled, and a forced telemetry submission remains unhandled
  - same-computer clone checks and Korean regional playtime are not answered: the server does not enable their client gates, so forced calls remain unhandled
  - native PLEX log UI integration and PLEX gateway ledger and notices are not implemented; the actual-client market walkthrough has not been run. A 40-case Python 2/production Rust fee comparison found two client-float differences.
  - modules whose effect is not implemented yet, among them mutadaptive remote armor repairers. Activating one is refused with a message, and `/effects unsupported` lists the effects tried since the server started.
  - in direct trades: items from cargo, from inside a container or from a corporation hangar, the active ship, fitted modules and charges, and PLEX; types that cannot be traded are refused anywhere in an offered container or ship
  - the GM bounty reimbursement and bounty cache calls
  - drone salvage, and reconnecting to drones whose control was lost; a lost drone stays its owner's and comes back with Return to Drone Bay, and an abandoned drone can be scooped
  - labels for personal contacts
  - LP store offers that cost Analysis Kredits: they are listed, but buying one is refused
  - nanite repair paste, heat repair while tethered, NPC overload, and repairs at structures
  - mutating items that are fitted, damaged, deployed in space, in a ship maintenance bay or owned by a corporation, and mutaplasmids that need extra inputs; mutated items cannot be renewed or reset
  - automatic compression, and compression at stations and structures; turning automatic compression on or off is refused with a message
  - survey scan results pushed by the scanner: the mining overlay gets them through its own scan call
  - corporation mining ledgers for moon-drilling structures
  - loot rights: any pilot whose ship is within a wreck's or cargo container's operational distance (2,500 m unless its type sets another) can take from it, and taking from someone else's does not make the pilot a suspect
  - control towers and their fleet hangars or ship maintenance facilities; ship bay sharing does not grant access to structures
  - structure inventory inspection and opening validation; inventory broker reads support station and solar-system roots, not structures
  - fighter, fuel and frigate escape bays are storage only: fighter launch, capital jump drives and escape into a stored frigate on ship loss are not supported
  - ordinary boarding of a foreign-owned unpiloted ship in space; taking a whole ship from an authorized maintenance bay is separate
  - wrecks, insurance payouts and killmails for an unpiloted ship destroyed in space. Its root and direct children are deleted regardless of owner, without guest compensation; deeper descendants and nested auxiliary records can remain orphaned. Pending reloads on the destroyed weapon ship are removed without refund, while a surviving external weapon's reservation remains for source-missing recovery.
  - custom crate selection and special skill-bundle or fitting rewards: `CustomOpenCrate`, `ClaimSkillBundle` and `ClaimFitting` are refused. The store does not sell crates. A crate whose contents are a skill bundle or a fitted ship cannot be previewed, and a crate whose contents are not known shows an empty preview.
  - audit log secure containers: they work as ordinary containers, with no password, audit log or item locking, and saving their settings is refused
  - structure SKIN activation and single-use SKIN license requests: these are deferred and explicitly refused without consuming an item; the store excludes unsupported single-use licenses
  - third-party SKINs are not implemented
- Voluntary `ship.Eject` remains unhandled; its interaction with an active Entosis link has not been exercised.
- Sovereignty source invalidation history rows are retained indefinitely.
- An industry job installed before this version whose blueprint has since been moved or destroyed is refused at delivery.
- Mining and salvage drones have no mass or agility in the static data; the server gives them the common light-drone values (3000 kg, agility 100). Drones with no targeting range or scan resolution in the static data lock at once within control range.
- The personal mining ledger starts with mining done after this version is installed.
- Crate contents that the static data does not list come from the server's own content, inferred from each crate's description; they are not the live server's reward tables.
- Crate opening has no request-keyed replay protection; client call IDs are fresh per call.
- A corporation at war that joins an alliance keeps its war, but the war no longer applies to its pilots, who now fight as the alliance, as the client also shows. The corporation's own CEO or directors can still retract it.
- A GM-created corporation can keep its CEO even if its saved member capacity is zero. Corporation capacity does not enforce racial membership restrictions.
- Corporation roles saved before scoped roles cannot show where a permission was meant to apply. The one-time migration keeps their old all-stations meaning by assigning local roles to headquarters, base and other stations, and keeps unknown historical bits without making them grantable. A server version without scoped roles is not a safe rollback target once the migration has run.
- The role-removal wait and the rule that a leaving member must be docked or fully offline are server rules. Granting a right again restarts the wait; only allowing future grants does not. A director's pending removal is cancelled if the member changes corporation or becomes CEO, or if the director loses the right to remove members.
- Corporation audit history starts when scoped roles are deployed; older logons and role changes are not reconstructed. The client's audit rows do not show whether a role applied to headquarters, base or other stations.
- The client's member list fills pages in order, so jumping to a page that was never fetched cannot fill the skipped pages.
- Membership, history and balance changes are saved before live refreshes are delivered. If the server stops immediately after a commit, the live updates can be missed; reconnecting rebuilds the saved state.
- Legacy corporation application renegotiation statuses remain readable but cannot be used to join.
- An alliance application takes effect immediately when accepted, although the client's acceptance dialog says there is a delay.
- Kill reports written before this version have no alliance recorded for the victim and the final blow, and these stay empty.
- In a war report the client lists a kill under a side only if the final blow came from that side, so a kill whose final blow came from a third party counts in the war's totals but appears in neither side's list.
- Fleet bubble broadcasts, fleet warp and fleet space visibility treat a whole solar system as one grid, because the server keeps one ballpark per system.
- Warp speed is rounded to the nearest milli-AU per second and floored at 500 milli-AU per second as server policy. Changes to a fit during a trip affect subsequent requests, not the current trip. Corruption warp-speed increases are not modelled.
- Ordinary warp pricing uses effective fitted values at activation, while the requested warp speed stays fixed. Many current imported hulls have zero warp capacitor need; that data does not establish the official policy for any other build. Capacitor balances are process-local and are not persisted across restart.
- After a shortened warp correction, especially when the ship has already stopped, the client retains its earlier interpolation history. Its displayed position and velocity can differ from the server for up to about one second, until the next update. A client that starts observing during the trip interpolates its initial view independently.
- SKIN visibility uses the existing one-ballpark-per-system approximation and respects cloaking. Regional eligibility is checked at writes using `server.boot_region`, which is immutable during a process; changing the region across a restart is unsupported.
- A license removal with no ship applications changes the database immediately but cannot send a ship removal event; the GM receives a policy message and an already displayed collection refreshes at the next login. A removal callback can arrive after the player selects another SKIN: the received legal cancel order remains authoritative, and there is no global ordering guarantee across Macho and gateway channels.
- Gateway notices are immediate, best-effort and not durably replayed. A full or closed queue cancels the slow stream generation rather than silently dropping notices; reconnect and a Get recover committed state.
- Shared item-filter and fleet-broadcast links are permanent and public: anyone signed in who has the whole link can open it, and a link cannot be made private, revoked or set to expire. Overview profile links are not supported.
- A pilot who changes corporation or alliance gains or loses access to shared bookmark folders at once, but a shared folder the client already shows stays in its list until the pilot logs in again.
- The daily Alpha skill injector can be used once per character in any 24 hours, counted from each use; this is the server's own rule.
- The client reads the Omega end date in two units: its clone-grade service expects Unix nanoseconds and the character selection screen expects Windows FILETIME. The server sends Unix nanoseconds, so the Omega time left on character selection is wrong. An Omega grade with no end date is sent as 31 December 2100.
- Mailing lists are free: a request to charge for mail to a list is refused. A list's owner cannot hand it over. List names are compared after PostgreSQL folds their case, which can differ from the client for a few Unicode letters.
- Search words are checked against the client's moderation rules. Where a rule ignores case, the server also treats the Kelvin sign (U+212A) and the long s (U+017F) as the letters k and s, which the client does not, so a search containing them can be refused where the client would allow it.
- A public gateway request, such as a skill plan change, is checked against the calling account and character, not against one game session. A request sent just before a relog therefore applies to the character's state after it.
- Corporation skill plans and corporation milestone progress are not implemented. Personal milestone completion is a reversible snapshot; no completion notification or historical completion timestamp is generated.
- Legacy milestone targets whose native prerequisite closure contains a cycle have invalid, incomplete derived progress with zero SP until the static graph is corrected; they do not block delivery.
- Live gateway notifications, unlike those persistent requests, are bound to the authoritative exact online session generation and cannot adopt a replacement session. Account and character ownership lookup is not token authentication: the public gateway requires a trusted network or authentication front door and must not be exposed directly to untrusted clients.
- Some runtime state lives only in memory and is lost when the server restarts:
  - fleets, with their finder adverts, member options, watchlists and target tags; combat and Crimewatch timers, ECM jams, tractor pulls, and in-progress hacking; a suspect flag from an activated kill right is the exception and is restored with its original deadline;
  - everything spawned into space except ships (NPCs, wrecks, scheduled effects);
  - drone orders and control, the drone settings the client sends before each launch, and ore a mining drone is carrying back;
  - a ship's velocity, warp and cloak, so a restarted ship starts at rest;
  - simulated pilot presence; scripts restore online simulated pilots after a restart. Simulated pilots have no client connection and no custom portrait, so the client shows its missing-portrait fallback.
- A reload still running when the server stops is not resumed. At the next start its charges return to their reservation owner's original location and flag if the source still exists and is owned by that owner; only if it has disappeared or changed owner do they return to the reload ship's cargo. Shared reload charges belong to the acting pilot from reservation, not the guest source owner. A valid original ordinary container exchanges its reserved space for the returned charges even if full or overfull. A fallback destination needs room, and ship holds still require an existing, nonzero applicable hold; if the destination refuses, the reservation is retained for a later restart.
- A refund group is limited to one positive signed 64-bit total quantity; an aggregate above that limit is refused rather than split into multiple business operations. Reload completion is also bounded by the resulting individual charge row's signed 64-bit quantity.
- Dogma quantity projections use floating-point values and are not authoritative exact inventory counts at large magnitudes.
- Item quantities above 99,999,999,999,999 are sent to the client as 99,999,999,999,999 for display; their authoritative server quantities remain unchanged.
- Same-type stack replacements do not need extra hold space when they do not increase current fill; hold type and zero-capacity restrictions still apply.
- Ordinary cargo, secure, audit-log secure and freight containers enforce their static self-capacity. This does not extend that quota to wrecks, exploration or trade containers, courier wraps, stations or offices, nor change contract semantics; ship holds retain their effective capacity and acceptance rules.
- The client's container display and local capacity precheck use only the physical rows returned by `List`, not server-only pending reload reservations; a move may pass that precheck and still be refused by server admission.
- A ship's position in space is saved when its pilot leaves the game, and every 30 seconds while it moves. A crash therefore loses at most the last 30 seconds of movement.
- Ship and drone condition in space changes in actor memory and dirty persistent condition is batch-saved with the position snapshot, every 30 seconds by default, and at docking, jump or transfer, boarding or ship swap, logoff and shutdown; drone condition is also saved on return to the bay. Shields recharge from the saved timestamp. A crash can lose condition changes since the last successful checkpoint; failed or delayed saves can extend that window. NPC health and attacker contributions live only in memory, and contributions are lost on restart.
- Nonlethal hit observations follow the memory change, not a database commit. Client notifications and Lua delivery following a committed ship loss are not replayed; a crash after commit can lose them, but not the committed loss, killmail or payout.
- Combat damage and remote-repair progress for daily goals, achievements and projects can appear up to one checkpoint interval (30 seconds by default) plus delivery time later. A forced stop can lose one checkpoint window and an in-flight batch; during a database outage it can lose buffered facts for longer. If the bounded buffer fills, new damage and remote-repair cycles do not take effect, and new warp scramble applications and refreshes are refused until capacity is available. An active scramble can also end when its continuation cannot be reserved at a checkpoint or eligibility change.
- When a ship is lost, the pilot's session moves into the capsule after the loss is saved. A pilot logging in again at that exact moment can register a new session between the server's last check and that move; the saved capsule is authoritative, and the next login, undock or boarding shows it.
- A replacement login during a logoff commit can leave a stale displayed logoff time while the character is online; current online status comes from the live session, not that timestamp.
- Store and stored-ship boarding use session- and actor-fenced settlement rather than replaying a stale transition into a replacement actor. If the actor stops while the database is unavailable, the call can return a transient error without deciding that an unknown transaction outcome aborted; once the database is available, a replacement login restores the durable selected ship.
- Undocking and launching a ship from a maintenance bay share a post-commit space publication path. If the database commit outcome is uncertain while the system actor remains alive, a committed ship can miss live world publication; the error does not establish that the transaction aborted. This is a source-derived limitation, not an observed runtime failure.
- Stopping the server with Ctrl-C or SIGTERM (`docker compose stop`) first stops starting scheduled jobs and gives the running ones up to `scheduler.drain_secs` to finish, then flushes changed positions and dirty persistent ship and drone condition before it exits. The server waits up to `server.shutdown_flush_timeout_secs` for these writes (10 seconds by default).
- With `space.collisions` on, collisions use one sphere per ship or celestial, as the client does by default, not the rendered shape: a ship can bump into empty space near a station, or pass through parts of it that stick out of its sphere. Station exit channels are used without the station's own rotation, which the static data does not give. Dynamic orientation, formations and destiny's rarer ball modes are not implemented.
- Ships have no orientation of their own. A micro jump or a bomb goes along the ship's velocity, or along its last commanded heading when it is stopped, or along a fixed default direction when it has neither.
- ISK wallet balances and journal amounts use exact cents within the signed 36-digit cent domain, with nonnegative wallet balances; journal balance snapshots can use 37 digits. PLEX balances are stored with up to 36 integer digits. The client is sent at most the largest balance it displays without scientific notation: 1,000,000,000,000,000,000 ISK for a character wallet, 9,223,372,036,854,774,784 ISK for a corporation wallet, and 99,999,999,999,999 PLEX. A purchase can leave the displayed balance unchanged while the stored balance is debited, if both balances exceed the display cap. ISK reaches the client as a double, so above about 45 trillion ISK it can no longer show every cent.
- Market orders use exact cents for prices, escrow and postings, but other economy features such as contracts retain floating-point calculations and storage until migrated. Their computed postings are checked and rounded to cents at the wallet boundary; precision already lost in those calculations cannot be recovered there. Market fees are computed exactly; client estimates use floating point and can differ by one cent at exact half-cent ties, and by their own rounding error at notional amounts beyond double precision.
- The wallet journal starts with this version. Earlier market fills get their account identities, but no journal rows, fees or balance snapshots are reconstructed for them. Market cash movements and charged direct skill purchases are journalled; other ISK movements, such as transfers between wallets, write no journal rows. `account.GetJournal` and `account.GetJournalForAccounts` still return empty lists; the wallet window reads `account.GetTransactions`.
- Corporate market sells require a real NPC-station office hangar division; Upwell structures and shared ship bays are not market sources or destinations. NPC corporation public supply remains an empty deferred read. PLEX uses a player-only global book and personal account vault or corporate physical custody, not a corporation vault. Faction-warfare discounts and upgrades and nonzero SCC context are unsupported; ordinary NPC stations use zero SCC context.
- Native-client exercise of the market type-admission and overdue-repricing refusals remains outstanding.
- Once corporate orders exist, do not deploy an older personal-only settlement server. Stop service and preserve the ledger; settle with owner-aware code before any downgrade. Do not clear orders or destructively roll back the schema. Earlier ignored corporate intent and historical cash journals cannot be reconstructed.
- Corporate market trading uses the shared market policies and corporation permissions.
- Injector diminishing returns are calculated per unit from the character's skill-point total, rounded down; one non-diminishing charge exempts one large or small injector, not a mini injector.
- Injecting more than 10,000 injectors in one action is refused. The client has no message for that refusal, so the injector window shows a placeholder instead of a reason.
- A booster lasts its type's duration with the modifiers the static data defines. The current data defines no skill modifier for booster duration, so Biology does not lengthen boosters. A booster consumed before boosters had an expiry keeps an unknown expiry.
- Expert system definitions come from the imported static data; they could not be compared with the client's own copy. A refusal to install, extend or remove an expert system uses the server's own text, because the client has no message for it.
- Only expert systems with a documented retail price are sold: two, at historical public prices. The store does not reproduce the complete current official catalogue. Marking a period offer as bought before an external payment is not supported and is refused without changing anything; expert systems are bought with PLEX in the store.
- A `/dogma` override changes every value the server computes. The client's fitting window and HUD show it only for an attribute the ship's hull type has; for a module, or a ship attribute the hull type lacks, they keep showing the type's value, while Show Info in space shows the new one. The command's reply says so.
- Slash command conversation replies require an online chat connection; replies
  sent while offline are silently dropped and are not queued for later delivery.
