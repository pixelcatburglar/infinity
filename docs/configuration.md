# Configuration

The server reads `config.toml` from its working directory, or the file named by the `CONFIG` environment variable. Every key is optional: a missing file means the built-in defaults, and `config.example.toml` lists every key with its default and where the default comes from. The file is read once at start; changes need a restart. `docker-compose.yml` mounts `config.example.toml` as `/config.toml` and sets `DATABASE_URL`, `RUST_LOG` and `SYSTEM_CAPACITY`.

Documented environment overrides, including the operational mining and daily goals settings, win over the file; the file wins over the default. Game keys without a documented environment override are set only in the file.

The game sections, `[accounts]` through `[space]`, set the server's own rules: starting balances, fees and taxes, timers, limits, rewards, and spawn ranges and sizes. Their defaults are the values the server used before the file existed. Values the client checks itself, values from the static data, and the destiny physics constants cannot be changed. `characters.starting_isk` accepts 0 to 9,999,999,999,999.99 (an amount with more than 15 significant digits would not be stored exactly); `accounts.starting_plex` accepts 0 to 9,223,372,036,854,775,807.

Start-up stops with an error that names the file and the dotted key when a key is unknown or a value is invalid, including an invalid environment variable. Errors show numbers and `true`/`false` values only; strings such as passwords and connection URLs are never printed. The `configuration loaded` log line names the file (or `defaults`) and the database host, port, user, database name and pool size in use.

The auxiliary listeners have fixed server-policy bounds that are not configurable: the chat, gateway, image and CDN listeners each accept at most 256 connections at once and at most 16 from one address, closing further sockets at accept. A chat connection has 30 seconds to authenticate. An image or CDN request has 10 seconds, counted from accept, to send its request line of at most 8192 bytes, headers of at most 32768 bytes in total, and a body within the upload limit.

The admission defaults leave substantial headroom above a small observation of one tester's seven game connections: pending handshakes peaked at one per address and two across the process. This observation is not a production-capacity calibration; the per-address allowance also accommodates several clients behind one shared address (NAT). Login-failure history is held only in memory and starts empty after every restart. A full 4096-address table first removes expired records, then evicts the non-cooldown record with the oldest last failure. Active cooldowns are never evicted. If all records are in cooldown, a new address still undergoes the ordinary credential check, and at most one warning is logged per window.

A `/shutdown` plan is held only in memory and shares the signal teardown path, so under `restart: unless-stopped` a due plan is an announced restart: the server comes back by itself with no plan. For a maintenance stop, use `docker compose stop` instead.

SKIN expiry uses one durable scheduled deadline per character for the nearest finite license, at expiry plus one FILETIME tick: equality is still valid. The usual scheduler polling latency applies.

## Logs

The server always logs to stdout, which is what `docker compose logs` shows. With `logging.dir` set (for example `dir = "logs"`, or `LOG_DIR=logs`) it also writes the same lines, filtered the same way and without colour codes, to files in that directory, created at start; a directory it cannot create stops the start with an error. Files are named in UTC: `server.YYYY-MM-DD.log` daily, with `-HH` added hourly and `-HH-MM` added minutely, and `server.log` with `never`. Rotation is by time only: `keep_files` limits the number of files, not their size, and a `never` file grows without limit. A graceful stop writes out the last lines. In Docker, uncomment `LOG_DIR` and the logs volume in `docker-compose.yml` to keep the files on the host. Logs can contain player information: keep them private and out of commits (`logs/` is ignored by Git).

A panic logs one `ERROR` event through the same logger, before the standard panic output, with five fields: `location` (the panic's source file and line when known), `message`, `thread`, the build's `commit` (see [build identity](development.md#build-identity)), and a forced `backtrace`. No `RUST_BACKTRACE` setting is needed, and the capture happens only when a panic fires, never on the normal path. The event follows the usual filter and `LOG_DIR`; the previous panic behavior, including the stderr message and the unwinding, is unchanged, so this is reporting, not recovery. A location names the exact source line, while release-build backtrace frames are not guaranteed line numbers. A process killed outright or aborting may exit before the non-blocking file writer flushes the record to disk.

When a thread panics while holding one of the server's shared synchronous locks, the lock is poisoned and the state it protected can no longer be trusted. The next thread to take that lock does not recover the data and does not answer its request with an error: it writes a fixed `FATAL` diagnostic to stderr naming the caller location, the build's `commit` and the exit code, then exits with code 1 after one best-effort `ERROR` event when it is not itself unwinding. The synchronous stderr write comes first because exiting skips the non-blocking file writer's final flush, so the last log event may never reach `logging.dir`. Whether the process restarts is the deployment's container policy, not the server's. Panics that never touch a shared lock keep the isolation described above.

Unless it poisons a shared synchronous lock, a panic while handling one client's request closes only that connection: the ordinary disconnect cleanup still runs once, logging the character off and releasing its ship and notification registration, and the connection ends normally rather than with the takeover's usurp message. Work already committed before the panic stays committed; a request panic never rolls back a completed transaction, and a panic inside a solar system's actor is outside this path. If the task that owns a session is dropped instead, the session waits for a request already in flight to finish, then runs the same ordinary cleanup; it is never interrupted mid-request. A second login taking over the account remains the only reason the server sends the usurp close. None of this is configurable.

A panic inside one solar system's actor marks that actor failed and keeps its closed handle until the pilots who were actually in it, and the work already admitted to its workers, have finished. Those pilots disconnect through their ordinary cleanup. A new entry into that system is refused until the failed handle is removed, and removal does not start another actor; the next explicit entry loads the last committed state. Other systems continue. The server does not save the failed actor's memory and does not restart it. A lost cleanup, worker, registry or binding proof uses the same stderr-first fatal exit as a poisoned shared lock. None of this is configurable.

### Economy lock diagnostics

The server logs `economy lock summary` at INFO on target `infinity_server::services::market::economy_lock`; the default `info` filter already shows it. A summary appears only when a reporting window closes: a window starts at a successful economy-lock acquisition and ends at the first successful acquisition at least 60 seconds of actual elapsed time later, so there is no line while the lock is idle, no background summary reporter, and no flush at exit. `count` covers completed operations only; `wait_*_ns` is queue time before acquisition and a cancelled caller leaves no sample. `hold_*_ns` is measured from acquisition to guard drop entry, excluding the short tail until the raw gate unlocks. The p50/p99 fields are fixed-bucket estimates; the maxima and `hold_total_ns` are exact. `utilization` is the ratio `hold_total_ns / window_ns` (a fraction, not a percent). `top_sites` names the up-to-five `file:line:column,count,hold_ns` call sites with the most hold time; when more distinct sites exist than the tracked capacity, `top_sites_complete` is `false`, `top_sites` is empty, and `site_overflow_count`/`site_overflow_hold_ns` carry the untracked operations. Sustained `wait_p99_ns` above 50,000,000 or `utilization` above 0.5 may warrant investigation. Missing lines do not prove the lock was never contended.

### Space tick diagnostics

The server logs `space tick attribution` at WARN and `space tick summary` at INFO on target `infinity_server::space::actor`; the default `info` filter already shows both. Every value is a top-level typed field; times are nanoseconds, except the per-tick `duration_us`/`lateness_us` in the existing TRACE line. A WARN line reports one system tick that took more than 20 ms of work or started more than 50 ms late: `steps`, `balls`/`observers`/`pilots`/`mailbox_depth`, the top three fixed tick phases, and the top three mailbox jobs and due timers by name (each with `count`, `total_ns`, `max_ns`). `own_lateness_ns` is an upper bound for the part the last mailbox job can explain and `runtime_lateness_ns` is the remainder, not proof of what delayed the tick. `delivery_*` counts synchronous destiny delivery, already included in the tick duration. A per-system limiter emits at most one line every 10 seconds and a process-wide ring at most five lines per rolling second; each rejected candidate adds one to `suppressed`. A `space tick summary` line appears only when a reception window closes: each actor merges its completed local window once it spans at least 60 seconds of actual time, and the process window closes at the first merge at least 60 seconds after it started, so during a pause a window can run longer; `window_ns` is always the actual span. Merging happens outside the measured tick, but a start it delays still shows in `lateness_*`. The first line after startup has `partial = true` because not every system has reported yet, and at most one local window per system arrives late to the next summary. The p50/p99 fields are fixed-bucket estimates merged from per-actor histograms; the maxima are true values, not averages. `mailbox_*`/`timer_*` totals and `ticks` cover every system including pilotless ones, while only windows that ever held a pilot enter the phase, function and system rankings. There is no background reporter and no flush at actor exit.

### Runtime diagnostics

The server reports completed RPC handlers, `System::defer` futures, scheduler handlers and durable progress delivery attempts. `runtime slow future` is a WARN when a completed future's longest poll strictly exceeds 20 ms or its total strictly exceeds one second; fields are `kind`, `name`, `total_ns`, `polls`, `poll_sum_ns` and `poll_max_ns`. Cancelled or panicking futures do not report completion. Poll durations are wall-clock time, including synchronous waits and OS preemption, not CPU accounting. RPC timing starts at the handler's first poll and includes response writing or error completion, but excludes network and pre-poll queueing; it is not network round-trip time. Deferred names are future type names, scheduler names are job kinds, and progress names are consumer keys. A progress sample includes preparation, the transaction, post-commit dispatch and failure bookkeeping; its enclosing scheduler sample can overlap, so the durations must not be added.

`rpc timing summary` is INFO on the first completion at least 60 seconds after the window opened; that boundary completion starts the next window. Fields are `window_ns`, `count`, `total_p50_ns`, `total_p99_ns`, `total_max_ns`, `overflow_calls`, `overflow_poll_sum_ns`, `overflow_poll_max_ns`, `top_poll_sum` and `top_poll_max`. Percentiles are fixed-bucket estimates. Up to 512 service/method pairs are tracked exactly per window; new names beyond the cap contribute to a single overflow bucket, while existing names remain exact. `overflow_calls` counts calls, not distinct names. Both top-five lists include the overflow bucket when eligible, so they are not necessarily exact rankings of all individual names. Lists use borrowed typed debug values with poll sum and max in nanoseconds. An unfinished window is not flushed at exit. Calls that fail before name resolution use an empty service/method pair, shown as `Rpc("", "")` in rankings and as `.` in slow-future warnings.

One task on the same Tokio runtime samples wake lateness every 100 ms, skips missed ticks without filling zero samples, and logs `runtime scheduling summary` at INFO after at least 60 seconds with `window_ns`, `samples`, `lateness_p50_ns`, `lateness_p99_ns` and `lateness_max_ns`. It also checks the economy lock holder approximately once per second. A hold strictly over 10 seconds logs `economy lock held too long` at ERROR with `file`, `line`, `column` and `held_ns`, repeating no more often than every 10 seconds while held. This task is not an independent watchdog: low lateness does not establish every worker is healthy, and it cannot run if all workers are synchronously blocked or the process is paused. Its last window is not flushed at exit.

### Database diagnostics

The server times completed database operations on target `infinity_server::db::timing`; the default `info` filter already shows both lines. Four kinds are measured: `checkout` (one pool connection wait), `statement` (one logical statement call, including `prepare_cached` on cached paths and counting each `batch_execute` as a single sample), `transaction` (one `Db::transaction` attempt, from just before its BEGIN to the end of its explicit COMMIT or ROLLBACK, each retry measured separately) and `commit` (one explicit COMMIT). Startup connection and schema work are timed the same way. A transaction built from an already-begun transaction records only its statements and an explicit `commit`; its `rollback` records nothing. A failed BEGIN and a cancelled or panicked operation record no sample, while an error on a completed call still counts. No SQL text or parameters are logged.

`database operation slow` is a WARN when a completed operation strictly exceeds its kind's threshold: checkout 50 ms, statement 100 ms, commit 100 ms, transaction 1 s. Fields are `kind`, `file`, `line`, `column`, `duration_ns`, `threshold_ns` and `overflow`; the location names the external call site, not the database wrapper. One site and kind warns at most every 10 seconds; a suppressed warning still counts. Before the server finishes binding its public listener the same message logs at INFO with an added `phase = "startup"` field; the thresholds and the ten-second throttle are unchanged.

`database timing summary` is an INFO line logged by the first completed operation at least 60 seconds after a window opened; that boundary operation also starts the next window, so an idle server logs nothing and nothing is flushed at exit. Fields are `window_ns` and a `per_kind` entry per kind with `count`, fixed-bucket `p50_ns`/`p99_ns`, true `max_ns`, `total_ns`, up to five `top` call sites ranked by total (each `file:line:column,count,total_ns,max_ns`) and the `overflow` count/total/max. Up to 512 distinct call sites are tracked exactly per kind; sites beyond that still count toward every total but appear only as overflow, and `top_complete=false` then marks the ranking as covering tracked sites only. There is no configuration or switch.

### Skill queue diagnostics

These logs help investigate skill queue exceptions; they do not fix them. The default filter `info,infinity_server=debug` already enables compact counts, a seven-field queue SHA-256 and other scalar details in the existing server log, not the whole queue. `RUST_LOG` overrides `logging.filter`; changing the filter requires a normal server restart, not a hot reload. For a targeted capture, set `RUST_LOG` to one of:

- `info,infinity_server::client::skill_queue=debug` for compact diagnostics.
- `info,infinity_server::client::skill_queue=trace` for the full allowed numeric queue and request fields during a short, opt-in reproduction window.
- `info,infinity_server=debug,infinity_server::client::skill_queue=trace` for that short window while retaining the other server DEBUG logs.

Do not enable global TRACE or raw connection TRACE. Afterwards restore the normal filter, or add `infinity_server::client::skill_queue=off` to disable this diagnostic; existing generic client DEBUG request lines may still appear.

Each selected RPC has one completion line, not an arrival line: `dispatch_start_ft` is the local dispatch start, `result_ready_ft` the result time, and `write_end_ft` the end of the response write when attempted. `reply_write` is `ok`, `failed`, or `not_attempted`. Notifications are logged after the socket write attempt. A successful write does not prove the client received or consumed it; a failed write may have sent partial bytes. Notification lines can precede an RPC completion line. Keep the original file order rather than sorting by timestamps.

No queue generation/version is currently available. Call IDs and times are correlation information, not versions. `queue_sha256` compares the same ordered seven fields and their `None` values across queue reads and queue notifications; compare free points separately. An ordinary wire digest is not a semantic version, and differing wire digests can reflect encoding order. Missing logs do not prove that a notification was never queued, and server logs cannot establish who owns or consumed a local UI snapshot.

If the same exception recurs, note the incident time and timezone, the deployed release or commit from deployment records (or `unknown`), the filter used, and a brief description of the actual UI actions. Convert the incident time to server UTC and privately provide **all** lines for target `infinity_server::client::skill_queue` for the same character and session, in original file order, from five minutes before through one minute after the incident, inclusive. Include purchase, free skill point preview and apply, save, reads, attribute reads, BeanCount, and all notification success and failure lines; do not select only the last two queue reads. Preserve digests, counts, activate source, write outcomes, call IDs and times. If a reconnect occurs, provide each session's continuous excerpt separately. Use the existing stdout or rotated server files; if the window crosses a UTC rotation, include the relevant excerpts from adjacent files.

An optional matching new `client-errors` section from the same time and exception can also help. A BeanCount repeat or an existing error ID does not prove a new traceback was uploaded; an old first report is not the current stack. Do not change log mode, delete database rows, or introduce a new capture framework for this diagnosis.

Logs contain private character, session and client IDs. Send excerpts only through a private support channel, never to the repository or a public issue. Redact unrelated names, IP addresses, tokens and free text; if IDs must be pseudonymized, use the same alias for each ID across all lines while retaining the diagnostic digests, counts, times and error correlation values.

## Client error reports

The client uploads the traceback of each exception the server has not seen before, and afterwards only reports how often it happens again. The server keeps one row per stack in `game.client_errors`: the first traceback (its last 64 KiB), when it was first and last seen, and the number of occurrences. In `D` mode each player's repeats go to `game.client_error_reports`. The crash notes a client sends at its next login go to `game.client_crashes`. With `logging.dir` set, each new traceback is also written in full (its last 1 MiB) to `client-errors` files next to the server files, named, rotated and kept the same way (`client-errors.YYYY-MM-DD.log` daily), while the server log gets one line per new error. To switch one error between counts and details, set its `log_mode` to `B` or `D`; the client picks the change up at its next report, normally within 15 minutes. A report that is malformed or over a limit (1024 records per call, 64 KiB per argument or crash text) is refused whole, and repeats that name another account's player are skipped. The first traceback for a stack is kept, so a modified client could send a false one first; delete that error's report rows and then the error row, and the next client to hit it uploads it again. Client performance statistics and the client's HTTP bug reports are not collected. Tracebacks contain file paths, local variables and session state from the player's machine: keep the database and the log files private.

```sql
SELECT error_id, mode, log_mode, occurrences, last_seen, left(traceback, 200)
FROM game.client_errors ORDER BY occurrences DESC LIMIT 20;
```
